# domain

Last verified: 2026-11-19

## Purpose
The logic between the MCP tools and Discord: errors, time, the live model, rendering, name resolution, pending, reading, triage, the send queue, the contribution log, opportunities, paced search, voice and cleanup.

## Structure
- `src/domain/errors.rs`: `Error`, `Result`.
- `src/domain/clock.rs`: `Timer`, `GapRng`, `SystemTimer`, `ThreadRng`, `now_ms`, and `fake::{FakeTimer, SeqGaps}` for tests.
- `src/domain/live.rs`: `LiveState`, `BufferPolicy`, `ConnState`, `LiveEvent`. Tests: `src/domain/live_tests.rs`, with fixtures from `src/test_support.rs`.
- `src/domain/render.rs`: `render_message`, `message_link`, `to_discord_mentions`. Tests: `src/domain/render_tests.rs`.
- `src/domain/resolve.rs`: `resolve_channel`, `resolve_server`, `resolve_user`, `channel_label`. Tests: `src/domain/resolve_tests.rs`.
- `src/domain/pending.rs`: `effective_watch`, `pending`, `get_pending`. Tests: `src/domain/pending_tests.rs`.
- `src/domain/reading.rs`: `read_history`, `search`, `list_servers`, `list_channels`, `channel_info`, `find_user`. Tests: `src/domain/reading_tests.rs`.
- `src/domain/triage.rs`: `mark_read`, `snooze`, `unsnooze`, `set_watch`. Tests: `src/domain/triage_tests.rs`.
- `src/domain/test_world.rs` (tests only): a connected `Ctx` over `FakeDiscord`, a READY fixture and an in-memory store.
- `src/domain/send_queue.rs`: `SendQueue`, the paced write queue. Tests: `src/domain/send_queue_tests.rs`.
- `src/domain/activity.rs`: the contribution log: `classify`, `record_own`, `spawn_recorder`, `backfill`, `my_activity`, plus `channel_label` and `message_link`. Tests: `src/domain/activity_tests.rs`.
- `src/domain/paced_search.rs`: `SearchPacer`, Discord search one at a time with a random 3–6 s gap, for every search tritone makes (search_messages, backfill, voice, cleanup). Tests: `src/domain/paced_search_tests.rs`.
- `src/domain/voice.rs`: tone profiles per category, notes per channel, categories, own-message samples through search. Tests: `src/domain/voice_tests.rs`.
- `src/domain/opportunities.rs`: the opportunity rules, the live scanner and `get_opportunities`. Tests: `src/domain/opportunities_tests.rs`.
- `src/domain/cleanup.rs`: `cleanup_plan` and `cleanup_apply`. Tests: `src/domain/cleanup_tests.rs`.
- `src/domain/test_api.rs` (`cfg(test)`): `Api`, a `FakeDiscord` wrapper that stamps each call with `FakeTimer` time and fails the nth call of a method once (`fail_on`, `fail_on_nth`).

## Public surface
- `Error` (`src/domain/errors.rs:6`): `Discord(DiscordError)`, `Ambiguous { query, candidates }`, `NotFound`, `Invalid`, `NotConnected`, `Store(anyhow::Error)`. The Display text goes to Claude and says what to do next; `kind()` (`src/domain/errors.rs:25`) is log-safe.
- `Timer` (`src/domain/clock.rs:10`): `now_ms`, `sleep_until`, `now_secs`. `now_ms(&dyn Timer)` (`src/domain/clock.rs:21`).
- `fake::FakeTimer` (`src/domain/clock.rs:63`): sleeping moves virtual time forward. `fake::SeqGaps` (`src/domain/clock.rs:87`): hands out gaps in order, then repeats the last.
- `LiveState` (`src/domain/live.rs:80`), interior `std::sync::Mutex`:
  - `new(BufferPolicy { per_channel, max_age_ms })` (`src/domain/live.rs:87`); starts `Connecting`.
  - `apply(GatewayEvent, now_ms)` (`src/domain/live.rs:124`): READY replaces the model (settings for guilds not in READY are dropped) and publishes `LiveEvent::Ready`; MESSAGE_CREATE bumps `last_message_id`, acks the channel when the user wrote it (any device), otherwise bumps `mention_count` for a DM, a direct mention, a mention of one of my roles (unless the server suppresses role mentions) or @everyone/@here (unless suppressed) (`pings_me`, `src/domain/live.rs:505`), buffers the text if the channel is buffered, and publishes `LiveEvent::Message { msg, own }`; MESSAGE_ACK sets the read state and publishes `LiveEvent::Acked`. A message in an unknown channel creates it (a DM when it has no guild). GUILD_UPDATE keeps channels and my roles; `MyRolesUpdate` replaces my roles. `RoleUpsert` adds or replaces one role; `RoleDelete` drops it from the guild's roles and from my roles (`src/domain/live.rs:175`). A channel update never moves `last_message_id` backwards, and never un-joins a thread: only `ThreadMembership` sets `joined` (`src/domain/live.rs:187`), so a THREAD_UPDATE (which carries no membership) keeps it.
  - `subscribe()` (`src/domain/live.rs:115`): a `tokio::sync::broadcast` receiver (capacity 1024).
  - Getters: `connection`, `me`, `guild`, `guilds`, `channel`, `channels`, `read_state` (default when unknown), `settings(Option<guild>)`, `user` (`src/domain/live.rs:258` onward). `users()` (`src/domain/live.rs:299`): every known user (READY users, DM recipients, authors seen, authors noted) plus me. `connection()` (`src/domain/live.rs:258`) is `Halted(e)` while a halt is set, else the gateway's state.
  - `note_authors(msgs)` (`src/domain/live.rs:311`): records the authors of REST pages (`read_history`, `read_thread`, `search_messages`, `get_pending`'s history pages and inbox) as people of their server (the message's `guild_id`, else its channel's), in memory only, at most 5,000 per server (`MAX_SEEN_PER_GUILD`, `src/domain/live.rs:25`); messages whose server isn't known are skipped. They also join `users`.
  - `guild_people(guild)` (`src/domain/live.rs:327`): the authors noted for that server plus the authors in its channels' buffers. Who an outgoing `@name` may reach.
  - Halts: `halt(e)` (`src/domain/live.rs:217`) stops every Discord call; `clear_halt()` (`src/domain/live.rs:223`) only on an explicit user action; `reject_token(token)` (`src/domain/live.rs:231`) halts with `NeedsLogin` and remembers the token's SHA-256, but ignores a token other than the current login once one is set (a stale client's late 401 can't halt a newer login); `try_login_with(token)` (`src/domain/live.rs:245`) refuses the rejected token (or one already tried since the halt), otherwise lifts the halt, sets `Connecting` and returns true.
  - `is_unread(channel)` (`src/domain/live.rs:342`): `last_message_id > last_acked`; a channel with messages and no read state counts as unread.
  - `discord_muted(channel, now_ms)` (`src/domain/live.rs:353`): any active mute on the guild, the channel, its category, or (for a thread) its parent and that one's category. A channel override with `muted:false` never unmutes a muted guild, as in the Discord client.
  - `can_view(channel)` (`src/domain/live.rs:375`): Discord's permission order (`channel_permissions`, `src/domain/live.rs:408`; https://docs.discord.food/topics/permissions#permission-overwrites). Owner and ADMINISTRATOR see everything; threads follow their parent; DMs are always visible; unknown channels are not.
  - `recent(channel)` (`src/domain/live.rs:390`): oldest first. `set_buffered(set)` (`src/domain/live.rs:396`): DMs and group DMs are always buffered; channels dropped from the set lose their text. The buffer prunes by count and age on insert.
  - `note_acked(channel, message)` (`src/domain/live.rs:210`): tritone acked over REST.
- `render_message(m, live) -> RenderedMessage` (`src/domain/render.rs:41`): `{ id, from (display name else username), from_id, at (RFC 3339 UTC), text, reply_to: Option<ReplyRef { message_id, author }>, reactions, link }`. In `text`, outside code (`map_outside_code`, `src/domain/render.rs:82`):
  - `<@id>`/`<@!id>` → `@label` or `@unknown-user`; `<#id>` → `#name` or `#unknown-channel`; custom emoji `<:name:id>`/`<a:name:id>` → `:name:` (`token_label`, `src/domain/render.rs:140`);
  - `<@&id>` → `@everyone` for the guild's own id, `@name` for a role the model knows with a name, else `@role:<id>` (`role_label`, `src/domain/render.rs:162`);
  - attachments (`[image: …]`, `[file: …]`) and embeds (`[embed: title]`) are appended one per line;
  - a reply whose author Discord didn't send (deleted message) has `author: "unknown-user"`.
  Syntax reference: https://docs.discord.food/reference#message-formatting
- `message_link(guild, channel, message)` (`src/domain/render.rs:71`): `https://discord.com/channels/{guild|@me}/{channel}/{message}`.
- `to_discord_mentions(text, live, channel, reply_to)` (`src/domain/render.rs:179`): `@name` → `<@id>` only when it can't reach the wrong person. Candidates: in a DM or group DM its recipients; in a server `guild_people` plus the author of the replied-to message when it's in the channel's buffer (never `users()`: a friend or someone seen in another server isn't in this one). A username matches exactly, any case; a display name only when one candidate has it (`unique_match`, `src/domain/render.rs:232`). An `@` counts only at the start, after whitespace or after `( [ { , ; : ! ? " ' * ~`, and never in a word holding `://` (`may_start_mention`, `src/domain/render.rs:199`); a name followed by `/` or `@` (`@scope/pkg`) is left alone. `@everyone`, `@here`, e-mail addresses, code, ambiguous and unknown names stay as written; a trailing `.` isn't part of the name. An unknown channel returns the text unchanged.
- `resolve_channel(query, live) -> Result<Id>` (`src/domain/resolve.rs:19`), in order: a bare id; a `discord.com/channels/{g|@me}/{c}[/{m}]` link (any subdomain); `@user` (1:1 DMs by username or display name); `server/#name`; `#name`; else a bare substring over server channels, 1:1 DMs and group DM names. Case-insensitive substring matching, but exact names win over partial ones (`#general` never matches `#general-help` when a `#general` exists). Server channels need `can_view`, a name (nameless phantom channels are skipped) and must not be categories. A known id or link to a hidden channel is `NotFound`; an unknown id passes through for Discord to answer. Several matches → `Error::Ambiguous` with up to 10 sorted labels, then "and N more: …" when cut, `Server › #channel (id)`, `@user (DM, id)` or `name (group DM, id)`.
- `resolve_server(query, live)` (`src/domain/resolve.rs:50`): an id, else part of the server name (exact names win); `Ambiguous` labels `Server (id)`.
- `resolve_user(query, live)` (`src/domain/resolve.rs:72`): an id (passed through), else part of a username or display name among `LiveState::users` other than me; `Ambiguous` labels `Name (@username, id)`.
- `channel_label(c, live)` (`src/domain/resolve.rs:183`): `@user (DM)`, `name (group DM)`, `Server › #channel`, `Server › #parent › thread`.
- `effective_watch(channel, live, watch: &WatchMap, now_ms)` (`src/domain/pending.rs:66`): an explicit level on the channel, then (threads) on its parent, then on its server; else a Discord mute (`discord_muted`) is `Muted`; else DMs and group DMs are `Full`, the rest `Normal`.
- `explicit_watch(channel, watch: &WatchMap) -> Option<WatchLevel>` (`src/domain/pending.rs:73`): the tritone-set part of that rule alone (the channel, a thread's parent, the server), with no live model; `effective_watch` and the gateway's `full_watch_channels` both use it, so there is one rule.
- `pending(live, store, mentions, now_ms) -> Result<Vec<PendingItem>>` (`src/domain/pending.rs:183`). `PendingItem { channel, label, reason, unread_count_hint, mention_count }`, `Reason { Dm, GroupDm, Mention, Reply, FullWatch, Thread }`. A channel counts only when listable (no categories, no nameless server channels, no thread the user hasn't joined unless its explicit watch (own, parent's, server's) is `Full`, as for a help forum on full watch: `listable(c, watch)`, `src/domain/pending.rs:105`), visible, unread, and not snoozed past now. Then:
  - an explicit tritone `Muted` (channel, parent or server) hides it entirely, mentions included;
  - a Discord mute without an explicit level: pending only for a **direct mention or a reply to me found in the messages themselves** (buffered messages plus the `mentions` inbox, newer than `last_acked`), never from `mention_count`, which also counts role and @everyone pings;
  - otherwise DM → `Dm`, group DM → `GroupDm`; a direct mention → `Mention`; a reply → `Reply`; an unsuppressed role or @everyone/@here ping (`ping_of`, `src/domain/pending.rs:128`) or Discord's `mention_count > 0` → `Mention`; `Full` → `FullWatch`; a joined thread → `Thread`.
  - Inbox direct mentions and replies in a channel that isn't listable (unknown, nameless, or an unjoined thread) are still pending (`unlisted_pings`, `src/domain/pending.rs:258`), reason `Mention` or `Reply`. The label is the channel's own (`Server › #parent › thread`) when tritone knows its name, else `<Server> › (thread or unknown channel)` from the message's `guild_id`. A ping in an unjoined thread comes only from the mentions inbox, not from buffered messages. Hidden only by an explicit tritone mute on that channel or its server, a snooze, or a read state past the message. Nameless channels without such a ping stay out (C5).
  - Order: DMs and group DMs, then mentions and replies, then full watch and threads; newest `last_message_id` first within each. `unread_count_hint` counts buffered unread messages (0 after a restart).
- `get_pending(ctx) -> PendingReport { pending, truncated }` (`src/domain/pending.rs:348`, `:309`): reads the mentions inbox in pages of 100 with `before` = the oldest id seen, until a page is short or reaches past 7 days, at most 5 pages (`inbox`, `src/domain/pending.rs:320`; `MAX_INBOX_PAGES`, `:60`). Role and @everyone pings share the inbox, so an older direct mention can sit pages down; `truncated` is true when the cap or a failed page stopped it. A non-halting failure logs its kind, keeps the pages read so far and falls back to read states and the buffer. Then it runs `pending` and notes the authors of the inbox and of each history page (`note_authors`), then for up to 15 kept entries (`MAX_FETCH`) fetches up to 20 unread messages with `history(after = last_acked, limit 21)` (`more_unread` when 21 come back), oldest first. **Never acks.** A channel with no read state at all is always fetched (within `MAX_CALLS` = 30 history calls) and dropped when the newest message is mine (Discord's rule: no read state means unread only if the last message isn't mine); dropped ones don't use the budget. Entries for unlisted channels aren't fetched: their `messages` are the inbox pings (with links), and `more_unread` is true. Mention and reply entries also carry `pings`: up to 5 pinging messages from the inbox or buffer that `messages` (the oldest unread) doesn't reach (`pings_outside`, `src/domain/pending.rs:413`). A halting error stops the call; any other per-channel error is reported on that entry.
- `read_history(ctx, channel, limit, before, peek) -> History` (`src/domain/reading.rs:82`): `{ channel_label, messages (oldest first), newest_id, more, ack_error? }`; `limit` clamped to 1..=100. Without `peek` and `before`, acks the newest message returned when it's past `last_acked`, then `live.note_acked`. A failed ack still returns the messages, with `ack_error`. `read_thread` is the same call on a thread id.
- `search(ctx, pacer, scope, query)` (`src/domain/reading.rs:120`): Discord search through `pacer` (the tool passes `SearchPacer::global()`), rendered.
- `list_servers` (`src/domain/reading.rs:133`), `list_channels` (`src/domain/reading.rs:201`), `channel_info` (`src/domain/reading.rs:232`): listings hide categories, nameless server channels, hidden channels, and muted ones (tritone or Discord) unless the `watch` filter asks for them; DMs and group DMs first, then by label. Servers muted in tritone are left out of `list_servers` unless `include_muted`.
- `find_user(live, query)` (`src/domain/reading.rs:243`): case-insensitive substring of username or display name over `LiveState::users` (not me), whole names first, at most 25; each with its 1:1 DM and the servers where tritone saw them write (from the buffer). No member search over REST.
- `mark_read(ctx, channels)` (`src/domain/triage.rs:25`): bulk ack of each unread channel to its `last_message_id`, chunks of 100, then `note_acked`; duplicates are dropped; channels with nothing unread cost no call (`already_read`); ids tritone doesn't know as channels are reported in `not_found`. `snooze` (`src/domain/triage.rs:50`) refuses past times; `unsnooze`; `set_watch(ctx, target, kind, level)` (`src/domain/triage.rs:67`): `kind` comes from the caller when known (a `#name` is a channel), else from `live`; an id that is both a server and its default channel (older servers) needs `kind`, or it's `Invalid`. Unknown ids, or a kind that doesn't exist for the id, are `NotFound`.
- `SendQueue` (`src/domain/send_queue.rs:454`): one write at a time; the first goes at once, each later one waits a random `MIN_GAP_MS..=MAX_GAP_MS` (20–60 s) after the previous write, at most `HOURLY_CAP` (30) per rolling hour (`earliest`, `src/domain/send_queue.rs:340`). Constants at `src/domain/send_queue.rs:38`.
  - `new(store, live, config, timer, rng)` (`src/domain/send_queue.rs:466`).
  - `attach(api)` (`src/domain/send_queue.rs:498`): the REST client. The write tools attach `ctx.api` on every enqueue, so a client rebuilt after a login is picked up; attaching never lifts a pause.
  - `enqueue(JobSpec)` (`src/domain/send_queue.rs:503`) → `Enqueued { job_id, position, eta_secs, note }`. `JobSpec` (`src/domain/send_queue.rs:63`): `Send { channel, content, reply_to, kind }`, `React { channel, message, emoji }`, `Thread { channel, from_message, name, content }`, `ForumPost { forum, name, content }`. Blank text, names or emoji are `Invalid`. The target label and guild are taken from `LiveState` at enqueue.
  - `status(job_id)` (`src/domain/send_queue.rs:555`) → `QueueStatus { jobs: Vec<JobView>, paused, writes_last_hour, hourly_cap }`. `JobView` (`src/domain/send_queue.rs:193`): `what`, `target`, `status` (`queued`, `sending`, `sent`, `failed`, `unknown`), `eta_secs`, `sent_message_id`, `thread_id`, `link`, `sent_at`, `error`, `ack_error`, `unseen` (`UnseenMessage { id, from, from_id, at, text }`, `src/domain/send_queue.rs:150`), `unseen_more`, `unseen_error`. The last 50 finished jobs are kept.
  - `resume()` (`src/domain/send_queue.rs:585`): the user's "continue". Refuses while `live.connection()` is `Halted(NeedsLogin)` (run `tritone login`) or `Halted(GatewayClosed)` / `Halted(SessionRefused)` (restart tritone). Otherwise calls `live.clear_halt()` and the attached client's `DiscordApi::clear_halt()` (its own sticky halt), then clears the pause only when the connection is `Ready`. After `Blocked { retry_after_s }` (in `live` or the queue's pause) it sets `paused_until_ms` to the time the pause was set (else now) + `retry_after_s`, so the block's Retry-After still holds.
  - `run()` (`src/domain/send_queue.rs:631`) loops over `step()` (`src/domain/send_queue.rs:649`), which returns `Idle` (empty, paused, no client), `NotReady` (connection not `Ready`; `run` polls every 5 s), `Waited` or `Processed`.
  - A Send, a Thread with content and a ForumPost first call `typing` and wait a random `TYPING_MIN_MS..=TYPING_MAX_MS` (2–5 s) through `Timer` (`type_for_a_while`, `src/domain/send_queue.rs:705`). Reactions skip typing but keep the gaps. A thread's first message types in the new thread.
  - The nonce is a snowflake of the send time with a 12-bit counter (`nonce_for`, `src/domain/send_queue.rs:694`), made at the first attempt and reused by the retry; forum posts pass it to `create_forum_post` (which doesn't send it).
  - After a posted message (`on_done`, `src/domain/send_queue.rs:834`): `record_own(.., via_tritone = true)`; for a Send, `check_unseen` (`src/domain/send_queue.rs:788`); then `ack(channel, message)` and `live.note_acked`. An ack failure sets `ack_error` and never fails the job.
  - Unseen (`mark_unseen_window`, `src/domain/send_queue.rs:736`): just before a Send's send call, the job notes where unseen starts (the later of the read point at enqueue and the current one, else the enqueue time; taken before the send because the send's own echo acks the channel) and the channel's newest message id. Only if that newest id is past the start does `check_unseen` read `history(after = start, 50)` and keep others' messages older than the sent one, oldest first, at most 20 (`unseen_more` beyond). A message arriving during the send call's own round trip isn't caught. Unseen text stays in the job's memory only, like the job's own text did.
  - Pacing: every attempt that reached Discord, sent, failed or unknown, updates the last write time and the hourly window (`note_write`, `src/domain/send_queue.rs:910`), saved in `kv` `send_pacing` as `{last_write_ms, window}` and loaded by `new`, so a restart can't burst.
  - Unknown outcome (`outcome_unknown`, `src/domain/send_queue.rs:294`): `Http(_)`, or `Api` with a 5xx or 2xx status (a reply that couldn't be read). A nonce'd send (`send_nonced`, `src/domain/send_queue.rs:715`) is sent again once after 2 s with the same nonce (Discord delivers a repeated nonce once only "in a short period of time", https://docs.discord.food/resources/message#create-message); if that also fails, or for a write without a nonce (thread creation, forum post, reaction), the job becomes `unknown` with "may have been sent: check the channel (read_history) before queueing it again" (`mark_unknown`). A failure of `typing` is a plain failure: nothing was written.
  - Errors (`on_error`, `src/domain/send_queue.rs:871`): a halting error fails the job (or marks it `unknown` after an unknown first attempt), pauses the queue with the other jobs still queued, and halts all of tritone through `live.halt(e)` unless `live` is already halted (`halt`, `src/domain/send_queue.rs:926`), which keeps a token the REST client already rejected. `RateLimited` pauses every later write until its Retry-After (capped at 600 s) and is retried once, with the same nonce, only when the retry can just re-send a nonce'd message (`nonce_protected`, `src/domain/send_queue.rs:417`): a Send, or a thread whose creation already succeeded. Thread creation, forum posts (`create_forum_post` sends no nonce) and reactions are never retried. A rate limit after an unknown first attempt is not retried later (the nonce window may have passed): the job becomes `unknown`. Anything else fails only that job, with no retry.
  - `step` pauses the queue (without failing jobs) when it finds `live` halted by something else.
- `classify(msg, channel, live, topics) -> String` (`src/domain/activity.rs:111`): a topic keyword in the message, or in the message it replies to, gives the topic's `kind`; so does a reply in a channel or thread whose name (or its parent's) matches a topic; a reply to a question (`looks_like_question`, `src/domain/activity.rs:94`: a `?` or a question opener) gives `answer`; else `other`. Keywords match whole words, any case (`topic_for`, `src/domain/activity.rs:89`). The replied-to message comes from the live buffer only, so outside full-watch channels a reply can only match by its own text or the channel name.
- `record_own(store, live, topics, msg, guild_hint, kind, via_tritone)` (`src/domain/activity.rs:137`): logs one of the user's own server messages (DMs are skipped). The guild comes from the message, else its channel, else `guild_hint`. The kind is the explicit one, else `classify`. Insert-or-ignore; when the row already existed, `via_tritone` flips it and an explicit `kind` overrides it, so the gateway echo and the queue can land in either order.
- `spawn_recorder(live, store, config)` (`src/domain/activity.rs:174`): subscribes first, then logs every `LiveEvent::Message { own: true }`. A lagged receiver logs the skip count and goes on. Spawned in `cli/daemon.rs` before the gateway.
- `backfill(ctx, progress_key)` (`src/domain/activity.rs:247`) / `backfill_with(.., pacer)` (`src/domain/activity.rs:251`) → `BackfillReport { guilds_done, guilds_total, recorded, messages_seen }`. Per guild (by id), `search(Guild(g), author_id = me, offset)`, 25 per page, through the shared `SearchPacer` (`backfill` uses `global()`), so its pages never run alongside another search and the 3–6 s gap and the `Indexing`/`RateLimited` waits (3 per page) come from the pacer. Past offset 9975, the limit in https://docs.discord.food/resources/message#search-guild-messages, it switches to a `max_id` cursor at the oldest id seen. `Forbidden`/`NotFound` skip the guild. Before each page it stops (progress kept) if `live` is halted by anything else. A halting error halts tritone (through the pacer) and returns it; any other error, including an index still not ready after the pacer's waits, returns it with progress kept. Progress is saved after every page in `kv` `<progress_key>:<guild>` as JSON `{offset, max_id, total, done, seen}`. Rows are `via_tritone = false`.
- `backfill_progress(store, live, key)` (`src/domain/activity.rs:230`): the same report from `kv`, without searching.
- `my_activity(store, live, from_ms, to_ms)` (`src/domain/activity.rs:380`) → `ActivitySummary { from, to, total, by_kind, by_server, by_channel, messages }`: counts (most first, then by label) and `ActivityLink { link, at, kind, server, channel, is_reply, via_tritone }` for the newest 50.

## Gotchas & invariants
- `fake` is `#[cfg(test)]`: tests only.
- `LiveEvent::Message` holds the `Message` unboxed on purpose (nearly every event is one), hence the `large_enum_variant` allow.
- `mention_count` from READY is authoritative; live increments follow the same rule as Discord's badge (direct, my roles, @everyone/@here, with the server's suppress settings).
- Queue text lives only in memory and is dropped when the job finishes; a restart drops unsent jobs. A job is retried only where a nonce makes the retry safe (once after a rate limit, once promptly after an unknown outcome); a write that may have gone out is `unknown`, never `failed`, so it isn't approved and sent twice.
- `SendQueue::resume` is the only path that calls `live.clear_halt()` and `DiscordApi::clear_halt()`, and only the `resume_queue` tool (on the user's explicit OK) calls it. The tool first attaches the client `AppState` holds now.
- Voice never stores message text: samples come from search on each `get_voice` call that needs them. `own_message` keeps ids and times for 22 days (`OWN_MESSAGE_KEEP_MS`), enough for the 21-day staleness window. DMs sent through tritone are not in the contribution log, so they still count toward a DM's staleness.
- `cleanup_plan` is bounded to 8 searches per call so the tool returns in under a minute; callers loop while `lookups_pending > 0`.
- Every Discord search goes through `SearchPacer::global()` (search_messages, backfill, voice, cleanup), so a backfill running in the background and a tool call queue up behind one another: a tool call that searches can wait for the backfill's current page and gap. Tests pass their own `SearchPacer::new` so fake clocks don't share state.
- A halt is separate from the gateway's state: Disconnected, RESUMED and READY never lift it, so a routine reconnect can't silently resume after a CAPTCHA or a block.

- `render` leaves fenced and inline code verbatim, like the Discord client; an unclosed fence is plain text.
- Ambiguous labels carry the id, because the error tells Claude to pass the id.
- `pending` reads store watch levels and snoozes but never writes. Only `read_history` (not peeking), `mark_read` and sending ack.
- The domain functions take a `Ctx` (`src/mcp/state.rs`) where they need the REST client, so tests build one over `FakeDiscord` (`test_world`).
